# 地图编辑器 · 可行性评估

> **状态：五项待决问题已于 2026-10-28 全部确认，方案见 [MAP_EDITOR_DESIGN.md](MAP_EDITOR_DESIGN.md)。本文保留为评估过程记录。**
> 定下来的五条：尺寸只对新建图开放 / layout.json 升为唯一源 / 只做朝向+视图旋转 / 第一版只服务临海路 / 要实时校验。
>
> 评估对象：可自选尺寸、按类别摆放物块、支持方向/旋转、可放敌人出生点的地图编辑器。
> 评估基准：当前 `临海路旧街区`（72×56）及其数据管线。

## 结论先说

**能建，而且基础比一般项目好**——地图本来就是"JSON + 纯函数校验器"，不是画在代码里的像素图。
真正的工作量不在编辑器 UI，而在两件容易被低估的事：

1. **把写死的地图参数化**。`validate.cjs` 里有 20 余处硬编码（72×56、48 容器、24 敌人、5 栋建筑、2 个撤离点、
   运河 x30–35、银行安保链、3 条推荐路线）。"改尺寸"是 3 行数据的事，**让新尺寸重新通过验收**才是大头。
2. **方向美术**（**本条初评有误，已更正**）。渲染器支持朝向，实测 `_side` **16 张**、`_back` **14 张**，
   14 种家具三向齐全——`tree_courtyard_back` 后来也补上了，朝向美术**没有缺口**。
   当初按 4 张 / 0 张估算的"补图工作量"不成立。

按范围分三档：

| 档 | 范围 | 主要新写的东西 | 相对工作量 |
| --- | --- | --- | --- |
| **A 最小可用** | 刷地块、放容器/敌人/门、实时校验、导出 JSON。尺寸固定 72×56 | 编辑器 UI + 校验器浏览器化 | 小 |
| **B 完整** | + 新建时选尺寸、实体属性面板、约束热区、区域/净宽绘制、撤销重做 | 校验器参数化（改 8/13 项）、路线生成 | 中偏大 |
| **C 生产化** | + 多地图注册、方向美术接入、与 build 一键联动 | 渲染与美术改造、地图注册表 | 大 |

建议先做 A，用它把现有这张图重画一遍——**如果 A 画不出临海路，B 也不用做**。

## 一、现状盘点

**地图与渲染**

- 72×56 格，1 格 32px，坐标左上角起、x 东 y 南。
- **正交俯视，没有透视**。地块是 `drawImage(img, sx, sy, 32, 32)`，精灵以格子中心贴图，无高度、无缩放。
  这一点决定了"切换透视方向"只能做到"旋转格子"，看不到侧面。
- 单地图：`RAID_MAP` 是唯一常量，没有 map 注册表，`M` 直接由它构建。

**数据形态**（`layout.json`，33 个顶层字段）

| 层 | 内容 | 数量 |
| --- | --- | ---: |
| 地形 | `rows` 56 行字符串 + 14 种字符的 `legend`（可走/可透/颜色） | 4032 格 |
| 区域 | buildings / rooms / clearances / tide.zones | 5 / 24 / 28 / 3 |
| 连接 | portals（门洞，带 connects）/ windows / bridges | 33 / 2 / 2 |
| 实体 | props（家具，含 solid/facing）/ containers（含 preference）/ enemies（含 patrolRadius） | 40 / 48 / 24 |
| 元数据 | spawn / exits / quotas / routeSpecs / routes | 1 / 2 / 按分区 / 3 / 3 |

**管线**（三跳，全部是 Node 脚本）

```
source.cjs ──build.cjs──> layout.json ──build-linhai-map.js──> js/data.js(RAID_MAP) ──build.js──> 潮汐线.html
     │                        │
     └── 也生成 figures/*.png、index.html、validation.json
                              └── validate.cjs 13 项验收
```

**现有校验**（`validate.cjs`，13 项，纯函数）

连通性 BFS（全图无孤岛、撤离点可达）、箱柜有操作面、净宽（主街 6 / 支巷 3 / 室内 2）、
双桥唯一跨岸、每栋建筑两处独立入口、银行必须过安保链、分区配额、敌人间距 3 格 / 距出生 12 格 / 撤离 6 格、
实体不压门洞桥面、路线可行。这套规则本身就是编辑器的"实时提示"来源。

**现有美术**

- 地块 12 张：wall / low / floor / street_stone / courtyard_paving / canal_water / quay_top /
  bridge_stone_deck / bridge_wood_deck / canal_steps_e / canal_steps_w / marsh。
- 道具 **90 张**（60 个基名），其中 `_side` 变体 **16 张**、`_back` 变体 **14 张**；
  14 种家具三向齐全，`tree_courtyard` 仅缺 `_back`，`door`/`sdoor` 不需要 `_back`。
- 方向是靠**命名变体**表达的，不是靠旋转：`door` / `door_side`、`sdoor` / `sdoor_side`、
  `bridge_*_rail_n` / `_s`、`canal_bank_e` / `_w`、`wall_breach_n` / `_s`、`shop_window_ns`。

**顺带发现两处文档漂移**：`README.md` 与校验项标题都写"41 个容器"，实际 `containers` 是 **48**
（`quotas.containers` 也是 48，校验断言也是 48）。41 是早期数字，一直没跟着改。
这类"人肉维护的计数"正是编辑器侧栏应该常驻显示的——不是编辑器多了不起，是手写文档迟早会漂。

## 二、四项需求逐条评估

### 1. 自选地图尺寸 —— 中等偏难（难点不在编辑器）

编辑尺寸本身是改两个数字。难的是下游全都假定 72×56、48 容器、24 敌人、5 栋楼、2 个撤离点、运河在 x30–35。

| 位置 | 硬编码 | 换成可变后的处理 |
| --- | --- | --- |
| `validate.cjs` | 尺寸、实体数量、建筑数、撤离点数、运河坐标、银行安保链、3 条路线 | 拆成"通用规则"与"本图规则"两组，后者按地图配置开关 |
| `build.cjs` | README 段落、图稿视角列表、统计文案 | 按图生成或直接跳过 |
| `build-linhai-map.js` | visual 映射表、doors 轴判断、家具 art 映射 | **通用**，可原样复用 |
| `js/core.js` | `RAID_MAP` 单例 | 要做多图则需注册表 |

结论：**"新建一张不同尺寸的图"可行；"让现有这张图随时改尺寸"会破坏所有空间叙事**（街道 6 格、桥位、银行动线
都是按 72×56 推敲出来的），不建议。

### 2. 物块分类 —— 容易

现状已经很接近：地形有 14 种字符且带语义（可走/可透/颜色），实体天然分三类（props / containers / enemies），
区域类单独一层。缺的只是**面向编辑面板的粗分类**，一层 20 行的映射即可，不动数据：

| 面板分类 | 来源 |
| --- | --- |
| 地面 | `.` `r` `q` `i` `=` `-` `s` |
| 墙体 / 边界 | `#` `X` `k`，以及 props 里的 `wall_breach_*`、`shop_window_ns` |
| 容器 | containers 48 个，类型来自 `containerTypes`（24 种字母） |
| 装饰 / 家具 | props 40 个（solid 与否分开显示） |
| 场景交互 | portals（门洞）、windows（橱窗）、exits（撤离点）、spawn |
| 导航 / 危险区 | clearances（净宽带）、tide.zones（潮汐预留） |

### 3. 旋转与"透视方向" —— 必须拆成三件事，别混为一谈

**（a）视图旋转**（编辑器把整张图转 90° 看）：**容易**。纯 UI 变换，正交俯视旋转 90° 无信息损失。
它的真实价值是画墙更顺手（横墙/竖墙各有一个舒服的角度）。

**（b）对象朝向**（门、窗、栏杆、断墙朝哪边；家具正/侧/背）：**数据已支持，缺美术**。
- 门：`build-linhai-map.js` 已按墙体走向自动算 `axis`，贴图选 `door` / `door_side`——这套逻辑可以直接复用；
- 家具：`prop.facing` 支持 `front|side|back`，14 种家具三向贴图齐全（多格件另有 `_large` 放大版，见 5.6）；
- **编辑器能改，画面大多不变**。这是"看起来做完了、实际没效果"的典型陷阱。

**（c）地块旋转**（同一张贴图转 90°/180°）：**不建议**。
现在的 12 张地块是**烘焙了左上光源**的像素图，旋转会让阴影方向跟着转，整张图的统一光照立刻崩。
而且地块本身对称度高（地板、水面、铺装），旋转几乎没有收益。
现有做法是"方向变体命名"（`canal_steps_e` / `_w`），这才是对的路——需要时按需补一张，而不是给每块加旋转。

另外要纠正一个前提：**游戏是正交俯视，没有透视**。所以"物块根据视图切换透视方向"在渲染层没有对应物；
能做的是"编辑器切视图方向 + 物块选朝向"。

### 4. 敌人出生点 —— 容易，而且最划算

数据结构已有（`type` + `patrolRadius`），校验规则也已写好（间距 3 格、距出生 12 格、撤离点 6 格缓冲、
室内外不混）。编辑器只要把这三条约束**画成热区**（绿/黄/红），放置时即时反馈，
就比"画完再跑校验、然后逐条改"强得多。

这也顺带解决一个现存问题：容器偏好与敌人分布是两套配额（`quotas.regions`），
手工改很容易漂；编辑器可以在侧栏常驻"分区配额 8/3、6/2…"的实时计数。

## 三、三个必须先解决的架构问题

### ① 谁是"源"：`source.cjs` 还是 `layout.json`

`test.cjs` 有一条断言：

```js
assert.deepEqual(exported, require('./source.cjs').data, '导出草案必须与当前设计源一致');
```

也就是说 **layout.json 现在是产物，source.cjs 才是手工源**。编辑器如果直接写 layout.json，这条测试立刻红。

三条路：

1. **升 layout.json 为唯一源**（推荐）：`source.cjs` 归档为历史初始化脚本，`test.cjs` 从"比对"改成"只跑校验"；
2. 编辑器反向生成 `source.cjs` 代码 —— 不推荐，等于让工具输出代码；
3. 双写 —— 最差，迟早不一致。

### ② 浏览器写不了盘

`file://` 下没法直接改 `layout.json`。两条可行路径：

- **File System Access API**（Chrome/Edge 支持，需用户手势选文件）——体验最好，但仅限 Chromium；
- **导出 JSON + 一键复制 node 命令**（`node tools/build-linhai-map.js && node build.js`）——最稳，跨浏览器。

建议两者都做：能直接写就写，不能就降级为下载。

### ③ 校验器要能"一次报全部错"

现在 `pass()` 里用 `assert`，**第一个错就抛**，编辑器需要一次列出所有问题。
把 `pass()` 改成 `try/catch` 收集器、区分 error/warn，就能同时用于 CLI 与浏览器。

好消息：`validate(data)` 是纯函数，fs 只在 CLI 入口用（`if(require.main===module)`），
**浏览器里包一层 assert 就能直接跑**——实时校验这条最关键的能力，成本意外地低。

## 四、建议的实施方案

**A. 最小可用（先做这个）**

- 单页 `tools/map-editor/index.html`，无构建、无依赖，Canvas 画格子，SVG 画覆盖层；
- 左侧：14 种地形 + 6 类实体调色板；中间：可缩放平移的格子；右侧：属性 + 校验结果；
- 工具：画笔 / 矩形 / 油漆桶 / 橡皮 / 选择移动 / 实体放置；
- 校验：把 `validate.cjs` 包成浏览器版，改动后即时跑（含连通性 BFS，4032 格规模毫秒级）；
- 导出：JSON 下载 + 复制命令；
- **不做**：尺寸自定义、旋转美术、多地图。

目标是用它把现有 72×56 重画一遍，验证数据往返不丢字段（`layout.json` 33 个字段，编辑器只碰其中 8 个，
其余必须原样保留——这一点要在导出时做深比较测试）。

**B. 完整**

- 新建地图：选尺寸 → 生成边界墙 + 空地形 → 强制填 spawn / 2 个 exits 才能通过校验；
- `validate.cjs` 拆成 `validateCommon`（连通、重叠、净宽、缓冲）+ `validateMapX`（运河、银行、路线），
  后者按 `map.rules` 开关；
- 区域绘制：建筑矩形、房间、净宽带（拖动可调宽度）、潮汐区；
- 约束热区：敌人间距、出生/撤离缓冲、箱柜操作面；
- 撤销/重做（命令栈）、图层显隐、字段级 diff。

**C. 生产化**

- 多地图：`RAID_MAP` → `MAPS[id]`，加载与存档带 mapId；
- 方向美术接入：14 种家具已齐三向，无待补图；
- 与 build 一键联动（本地起一个 20 行的 Node 服务收 POST 写盘）。

## 五、风险清单

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 尺寸参数化 | 牵动 13 项校验里的 8 项 + 配额 + 路线生成，是最容易被低估的部分 | 先只支持"新建图"，不改造现有图 |
| 源冲突 | 编辑器写 layout.json 会撞 `test.cjs` 的比对断言 | 先定源，再写编辑器 |
| 方向美术 | 4 个方向 = 4 倍贴图；不做就是"能设不能看" | 只对门/窗/栏杆用方向（已有），家具保持 front |
| 往返丢字段 | layout.json 有 33 个字段，编辑器只编辑 8 个 | 导出前做 深比较，未触碰的字段必须逐字节一致 |
| 单文件游戏的隔离 | 编辑器不能直接改 `js/data.js`，必须走 Node | 导出 + 命令，或本地小服务 |
| 编辑器成为新源后 | 手改 JSON 与编辑器行为会逐渐漂 | 给编辑器加 UI 级冒烟测试（用 layout.json 往返一次） |

## 六、需要你决定的五件事

1. **尺寸**：只要求"新建图能选尺寸"，还是"现有临海路也要能改"？（后者会破坏空间叙事，不建议）
2. **源**：接受 `layout.json` 成为唯一源、`source.cjs` 退休吗？
3. **旋转**：接受"朝向选择器 + 视图旋转"，不做地块自由旋转吗？（地块旋转会破坏烘焙光照）
4. **范围**：第一版只服务临海路一张图，可以吗？
5. **校验**：要不要在浏览器里实时跑（需要把 `validate.cjs` 改成收集器）？我建议要，这是编辑器最大的价值点。

把这五条定下来，A 档可以直接开工；不定也能做，但很可能返工在"源"和"尺寸"这两处。
