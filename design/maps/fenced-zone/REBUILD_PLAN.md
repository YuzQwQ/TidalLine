# 围栏区重做方案（正式第二张地图）

> 结论先行：**围栏区不能靠"补元数据"升级成正式地图，必须重画地形。**
> 2026-11-12 收到新概念图《围栏区·临时安置点 布局原型》，主题与动线已定，
> 三项设计决策见第四节。工作目录 `design/maps/fenced-zone/`。

## 一、为什么改方案

最初判断是「复用现有 64×44 骨架，补齐 rooms / doors / lootSpawns / 命名区域即可，成本最低」。
实测反推后这个判断不成立：

- 以 `#` 和 `+` 为边界对全图做连通分量，只得 **10 个块**：
  一个 **1539 格的超大开放空间**，加 9 个面积 36–107 的房间。
- 8 个所谓「区域」大多是凹形半开放示意（L 形、十字形、U 形），
  外墙不闭合，也没有内墙切分。房间不是"没登记"，是**地形里根本不存在**。
- 反推稿只识别出 10 个房间，28 个门洞里大部分连不到两个封闭空间，
  共享校验器报 28 项硬错误（G7 撤离点敌人缓冲、G8 门洞连通、G10 路线航点）。

所以给旧快照补一层 JSON 字段，只会得到一张"元数据很全、玩法仍然空旷"的图。
任务系统要的是可寻址的封闭地点（房间、钥匙门、特定容器），那需要先有空间结构。

## 三、新概念图《围栏区·临时安置点》

四个功能区取代旧的 8 个抽象区域名：

| 区 | 名称 | 约尺寸 | 职能 |
| --- | --- | --- | --- |
| A | 登记所 | 14×10 | 人员登记、指挥与档案 |
| B | 安置营地 | 18×14 | 帐篷区、临时居住、生活物资 |
| C | 物资堆场 | 16×10 | 露天堆场、补给与集散 |
| D | 泵站 | 16×10 | 排水与供电设施、局部积水 |

**成立的地方**：主题有叙事链（登记 → 安置 → 补给 → 排水），比 8 个抽象区名更像一个真实地点；
主次道路分级（主路 4–6 格 / 次路 2–3 格）让主路成为交火带、次路成为潜行线；
三个撤离点分处北、西、东南，主入口在南，纵穿压力清晰；
橙色虚线帐篷 / 堆垛是现成的容器语言，可一比一映射成搜刮点。
**泵站 + 右下水域**是最值钱的组合：让涨潮从背景装饰变成玩法决策。

**原图不能直接落地之处**：四个区内部都是完整大开间，没有一道隔墙、一扇门
（散落的浅灰小方块才是「不可进入区域」）。按轮廓转成字符网格会重新得到"少量大连通块"，
任务系统依旧无处落点。故需在**不动外轮廓与道路**的前提下补内部结构，见第四节。

## 四、已定设计决策（2026-11-12）

1. **加隔墙与门（按建议切）**
   - A 登记所切 3 间：登记大厅 / 档案室 / 值班室；档案室上一把钥匙门，高价值情报集中于此。
   - D 泵站切 3 间：泵机房 / 配电室 / 阀组间；阀组间为开泵交互点，可上锁。
   - B 的 6 个帐篷、C 的 4 个堆垛用货架 / 矮墙围成半封闭隔间——可寻址、可绕行，
     但不做硬墙，保留营地开阔感。
   - 散落小建筑挑 2–3 个改成可进入的值班棚。
   - 目标约 14–16 个可寻址空间 + 10 扇门。
2. **主入口 = 固定入场点**（不算撤离点）
   每局固定从南门进入，从北 / 西 / 东南三选一撤离。需改 `DeployGuard` 与
   `Game.startRun` 的入场逻辑；动线最干净，也与涨潮压缩东南点的节奏吻合。
3. **泵站开泵交互，这版就做**
   涨潮第 3 阶段淹没东南撤离点；到 D 泵站阀组间开泵排水可保住该点，
   否则只能走北 / 西。水域从装饰变成真正的选择，D 区由此有非去不可的理由。
   泵状态只在本局有效，撤离 / 死亡即清除，不写存档。

### 容器 / 刷新点 / 敌人分布（按叙事分层，不平均撒）

- C 物资堆场：密集高价值（补给 / 弹药 / 工具）
- A 登记所：少而精（档案 / 钥匙）
- B 安置营地：量大价低（生活物资 / 医疗）
- D 泵站：偏工具电子
- 道路上少量垃圾容器
- 目标 ~120 容器 / ~60 刷新点 / ~40 敌人；守卫密度 C > D > A > B

### 边界处理

外圈栅栏转 `#`；4 个开口（北 / 西 / 东南 / 主入口）在边界内侧一格放 `E` / `P`，
避免共享校验器 G1 报"边界可通行"（旧 runtime 也是这么做的）。

### 编译管线的真实缺口

- `tools/build-linhai-map.js` 只编译临海路：`layout.json` → `RAID_MAP` 生成块。
- 它把 `buildings / clearances / plazas / routeSpecs` **全部丢弃**，
  `districts` 只由 buildings 现算。设计稿里 28 条命名街巷、2 个广场、3 条搜刮路线
  从未进入运行时。且 `layout.json` 自标「独立设计评审稿，未接入游戏」——设计与运行时脱节。
- `FENCED_MAP` 是直接读 `runtime.json` 原样塞进 `js/data.js`，**无编译、无校验**，
  只断言 `rows.length === 44` 且每行 64 字符。

## 七、POI 注册表规范

设计稿保留全部命名字段，编译期统一汇总成 `pois`，运行时可查询：

```js
{ id, mapId, name, type, rect, anchor, region, tags }
// type: building | room | bay | clearance | plaza | exit | entrance | container | lootSpawn
```

`js/map-poi.js` 提供 `POI.byMap(mapId)` / `POI.byType(mapId, type)` /
`POI.get(id)` / `POI.nearest(mapId, x, y)`。这样委托才能写成
「去登记所档案室取回卷宗」「在物资堆场清三个堆垛」「到泵站阀组间开泵」，
而不是永远只能「从仓库交材料」。信任解锁的高阶货物也才能绑定到具体产出地点。
